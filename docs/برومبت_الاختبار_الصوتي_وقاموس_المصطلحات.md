# برومبت تنفيذ ميزتين — الاختبار الصوتي (إعاقة حركية) + قاموس المصطلحات من السلايدات (الصمم/ضعف السمع)

هذا الملف فيه **مهمتان منفصلتان تمامًا**، كل وحدة موزّعة بين وكيلين (وكيل المنصة + وكيل التطبيق). **لا تلصق الملف كامل بجلسة واحدة** — انسخ القسم المخصص لكل وكيل بجلسته الصحيحة فقط، لأن كل وكيل يشتغل بمستودع كود مختلف.

# 🅰️ الميزة الأولى: الاختبار الصوتي للإعاقة الحركية

## الفكرة الكاملة (اقرأها قبل ما توزّع المهام)

الأستاذ ينشئ اختبار اختيار من متعدد (MCQ) بالمنصة — **بخيارين لإنشاء الأسئلة، حرية كاملة للأستاذ**:
- **يدوي:** يكتب الأسئلة والخيارات بنفسه
- **بالذكاء الاصطناعي:** يرفع سلايدات المحاضرة، والـ AI يولّد أسئلة اختيار من متعدد تلقائيًا منها (يراجعها الأستاذ ويعدّل عليها قبل الاعتماد، مو تنشر مباشرة بدون مراجعته)

الطالب ذو الإعاقة الحركية يفتح الاختبار بالتطبيق، **يسمع** السؤال والخيارات بدل ما يقرأها، **يجاوب بصوته** بدل ما يضغط، والتطبيق يحدد إجابته ويؤكدها له صوتيًا قبل الانتقال للسؤال التالي.

> **مؤقتًا الآن:** الأسئلة المقالية **خارج النطاق** — MCQ بس بهذي المرحلة. لا تبني تدفق التسجيل الحر أو إعادة الصياغة الآن (موضّح بقسم منفصل بالأسفل لو تبي تفعّله لاحقًا).

## 🖥️ قسم المنصة (Next.js) — الصق هذا بجلسة `D:\Shadow\platform`

### المهمة 1: نموذج قاعدة البيانات
أضف بـ `schema.prisma`:
- `Exam` (معرّف، عنوان، مرتبط بمقرر عبر `FacultyCourseLink`، تاريخ الإتاحة، مصدر الإنشاء: `MANUAL` أو `AI_GENERATED`)
- `Question` (نص السؤال، مرتبط بـ `Exam`) — **MCQ فقط بهذي المرحلة**، لكن أضف عمود `type` بقيمة افتراضية `MCQ` بالمخطط عشان لو فُعِّل المقالي لاحقًا ما يحتاج migration كبير من جديد
- `QuestionOption` (نص الخيار، مرتبط بـ `Question`)
- `ExamSubmission` (مرتبط بـ `Exam` و`User` الطالب، حالة: قيد التقديم/مكتمل)
- `Answer` (مرتبط بـ `Question` و`ExamSubmission`، يحتوي: معرّف الخيار المُختار + رابط التسجيل الصوتي للتأكيد)

نفّذ migration، وتأكد من عزل الصلاحيات: **فقط الأستاذ صاحب المقرر ينشئ/يرى الاختبار، فقط الطالب المسجَّل بالمقرر يقدّم إجابة، الإدارة والمختص لا علاقة لهم بهذا الجزء إطلاقًا** (بنفس منطق جدول الصلاحيات المعتمد بالمشروع).

### المهمة 2: واجهة الأستاذ لإنشاء الاختبار — بخيارين واضحين
صفحة إنشاء اختبار تعرض للأستاذ خيارين صريحين بالبداية:

**الخيار الأول — يدوي:** نموذج عادي: عنوان الاختبار، إضافة أسئلة MCQ بخياراتها يدويًا، حفظ.

**الخيار الثاني — بالذكاء الاصطناعي:** الأستاذ يرفع ملف سلايدات (PDF)، يحدد عدد الأسئلة المطلوب تقريبًا، ويضغط "توليد". النظام يستخدم Gemini API **من السيرفر** (نفس مبدأ حماية المفتاح المذكور بالمهمة 4 أدناه) بطلب واضح يولّد أسئلة MCQ (سؤال + 4 خيارات + تحديد الصحيح داخليًا للتصحيح المستقبلي) من محتوى السلايدات. **الأسئلة المولَّدة تُعرض للأستاذ كمسودة قابلة للتعديل والحذف والإضافة قبل أي اعتماد أو نشر للطلاب — لا تُنشر تلقائيًا بدون مراجعة بشرية.**

### المهمة 3: API لتقديم الاختبار للتطبيق
- `GET /api/exams/:id/questions` — يرجّع الأسئلة والخيارات (بدون الإجابة الصحيحة)
- `POST /api/exams/:id/answers` — يستقبل إجابة سؤال واحد (معرّف السؤال، معرّف الخيار المُختار، رابط الصوت المرفوع للتأكيد)

### المهمة 4 (اختيارية لكن موصى بها أمنيًا): نقطة نهاية TTS وسيطة
`POST /api/tts/generate` — يستقبل نصًا، يستدعي Gemini TTS من السيرفر، يرجّع رابط ملف صوتي أو الصوت مباشرة. **السبب:** لو التطبيق استدعى Gemini مباشرة، مفتاح الـ API يكون مُضمَّنًا داخل ملف APK ويمكن استخراجه بالهندسة العكسية من أي شخص يحمّل التطبيق — خطر أمني حقيقي. المرور عبر المنصة يبقي المفتاح على السيرفر فقط.

## 📱 قسم التطبيق (Flutter) — الصق هذا بجلسة `D:\Shadow\app`

### المهمة 1: شاشة الاختبار الصوتي داخل وضع الإعاقة الحركية
شاشة جديدة تُفتح من داخل التحكم الصوتي أو كخيار خامس بنفس الوضع. تعرض حالة: "جاري تحميل الاختبار" ثم تبدأ.

### المهمة 2: تدفق سؤال MCQ
1. اجلب السؤال من `GET /api/exams/:id/questions`
2. اقرأه صوتيًا (عبر نقطة النهاية الوسيطة بالمنصة من المهمة 4 أعلاه — **لا تستدعِ Gemini مباشرة من التطبيق**)
3. فعّل المايك، التقط إجابة الطالب عبر Deepgram (نفس الخدمة المستخدمة بوضع الصمم)
4. طابق النص الملتقط مع نصوص الخيارات بخوارزمية تطابق تقريبي (fuzzy matching — مكتبة `string_similarity` أو مشابه بـ Dart)
5. **اقرأ صوتيًا التأكيد إلزاميًا:** "فهمت: [نص الخيار] — صحيح؟" وانتظر تأكيد صوتي ("نعم"/"إعادة") قبل الإرسال والانتقال للسؤال التالي
6. أرسل الإجابة + رابط التسجيل الصوتي عبر `POST /api/exams/:id/answers`
7. انتقل تلقائيًا للسؤال التالي حتى نهاية الاختبار، ثم اعرض شاشة "تم التسليم"

> **الأسئلة المقالية خارج النطاق حاليًا** — لا تبني أي تدفق تسجيل حر أو إرسال لإعادة الصياغة بهذي المرحلة.

### المهمة 3: أهداف لمس واعتبارات إتاحة
كل زر بهذي الشاشة **≥48×48 نقطة** (القاعدة المعتمدة بالمشروع)، ولو أمكن، خلّ التنقل بين الأسئلة ممكن بالكامل بالصوت أيضًا (أمر "السؤال التالي" / "أعد السؤال") لمن حركته أصعب حتى من الضغط على زر تأكيد.

# 🅱️ الميزة الثانية: قاموس مصطلحات المحاضرة من السلايدات (الصمم/ضعف السمع)

## الفكرة الكاملة

الأستاذ يرفع سلايدات المحاضرة على المنصة **قبل** المحاضرة (أو بأي وقت). النظام يستخرج المصطلحات الإنجليزية التقنية منها تلقائيًا ويحفظها. لما الطالب يفتح وضع "تحويل الكلام لنص" بالتطبيق ويختار نفس المقرر/المحاضرة، يجلب التطبيق قائمة المصطلحات هذي، ويرسلها لـ Deepgram كـ `keyterm` مع كل طلب تفريغ — فيصير التمييز بين "عربي عادي" و"مصطلح إنجليزي بالمنتصف" أدق بكثير، **بدون أي تدريب موديل جديد** (موضّح بالتفصيل بالنقاش السابق).

## 🖥️ قسم المنصة (Next.js) — الصق هذا بجلسة `D:\Shadow\platform`

### المهمة 1: نموذج قاعدة البيانات
أضف جدول `LectureKeyterm` — مرتبط بـ `FacultyCourseLink` أو بمحاضرة محددة إن وُجد كيان "محاضرة" أصلًا بالمخطط (تحقق من `schema.prisma` أولًا)، يحتوي: نص المصطلح، مصدره (تلقائي من ملف / أضافه الأستاذ يدويًا).

### المهمة 2: استخراج المصطلحات من ملف PDF المرفوع
عند رفع سلايدات (استخدم مسار الرفع الموجود أصلًا بميزة `FacultyResource`/دعم التعلم إن كان قابلًا لإعادة الاستخدام):
1. استخرج النص من الـ PDF (مكتبة موجودة أصلًا بالمشروع لهذا الغرض على الأغلب — تحقق قبل ما تضيف مكتبة جديدة)
2. استخرج المصطلحات الإنجليزية: إما بـ regex بسيط (كلمات/عبارات لاتينية متتالية بحد أدنى حرفين) كخطوة أولى سريعة، **أو** أدق: مرّر النص لـ Gemini API بطلب صريح "استخرج المصطلحات التقنية الإنجليزية فقط من هذا النص، أعدها كقائمة JSON" — الخيار الثاني أدق ويميّز "المصطلح التقني" عن "أي كلمة إنجليزية عرضية"
3. احفظها بجدول `LectureKeyterm` مربوطة بالمقرر/المحاضرة
4. **اسمح للأستاذ يراجع القائمة المستخرجة ويعدّل عليها يدويًا** (يحذف/يضيف) قبل الاعتماد — الاستخراج التلقائي نقطة بداية، مو قرار نهائي

### المهمة 3: تحديث تراكمي
لو الأستاذ رفع ملفًا جديدًا لنفس المقرر لاحقًا بالترم، **أضف** للمصطلحات الموجودة (لا تستبدلها) — المعجم يتراكم لكل مقرر مع الوقت.

### المهمة 4: API للتطبيق
`GET /api/courses/:id/keyterms` — يرجّع قائمة نصية بكل المصطلحات المعتمدة لهذا المقرر. **تحقق الصلاحية:** فقط طالب مسجَّل فعليًا بهذا المقرر يقدر يستدعيها (استخدم نفس منطق فحص التسجيل الموجود أصلًا بالمشروع).

## 📱 قسم التطبيق (Flutter) — الصق هذا بجلسة `D:\Shadow\app`

### المهمة 1: اختيار المقرر قبل التسجيل
بشاشة "تحويل الكلام لنص"، أضف خطوة اختيار المقرر (قائمة منسدلة بمقررات الطالب — اجلبها من المنصة) **قبل** ما يضغط زر التسجيل. لو الطالب مسجَّل بمقرر واحد بس، اختره تلقائيًا بدون ما تزعجه بخطوة إضافية.

### المهمة 2: جلب المصطلحات وإرسالها لـ Deepgram
عند اختيار المقرر (أو تلقائيًا لو مقرر واحد):
1. استدعِ `GET /api/courses/:id/keyterms`
2. مرّر القائمة الناتجة كباراميتر `keyterm` (متعدد القيم) بكل طلب تفريغ لـ Deepgram طول الجلسة

### المهمة 3: التعامل مع غياب المصطلحات
لو المقرر ما فيه أي مصطلحات محفوظة بعد (الأستاذ ما رفع سلايدات)، **يعمل التطبيق عادي بدون توقف** — بس بدون تحسين الدقة الإضافي. لا تُظهر خطأ، فقط استمر بالتفريغ العادي.

# ✅ ترتيب التنفيذ الموصى به

1. ابدأ بـ **الميزة الثانية (قاموس المصطلحات)** أولًا — أبسط، بدون جداول اختبارات معقدة، وتحسّن نتيجة موجودة أصلًا فورًا
2. بعدها الميزة الأولى (الاختبار الصوتي) — أكبر، تحتاج جداول جديدة وشاشة كاملة جديدة

# ⚠️ قواعد العمل الثابتة (نفس المعتمدة بكل المشروع)

- **لا تقل "تم" بدون دليل فعلي** (سكرين شوت، أو نتيجة اختبار حقيقية تعمل من طرف لطرف: رفع سلايدات → ظهور مصطلحات → تفريغ محسّن، أو: إنشاء اختبار → إجابة صوتية → مراجعة أستاذ)
- **لا تضع أي مفتاح API مباشرة داخل كود Flutter** — كل استدعاء لخدمة AI يمر عبر المنصة (نقطة نهاية وسيطة)، بالضبط زي مهمة توليد الأسئلة ونقطة TTS الوسيطة بالميزة الأولى
- قف بعد كل مهمة رئيسية وأرِ نتيجة فعلية قبل الانتقال للتالية
